# dtc-mcp v1.1.0 plan — recipe-by-intent discovery

**Status:** draft, internal. Sketched before v1.0.5 re-bench completes; finalize after we see the v1.0.5 delta and know how much of the gap remains attributable to discovery (vs the stash-and-cite fix).

## Goal

Close the **discovery tax** identified in `findings.md` lessons #4, #5, #7. The bench surfaced that documented workarounds (e.g. `additional-fields[segment]=profile_count`) existed but the agent had to rediscover them on each run, costing 100–300s of wall-clock and 30–60k tokens of exploration per affected task.

The fix in two halves, shipped together as v1.1.0:

1. **Restructure docs as intent-indexed recipes** (backlog #3). Move from "API reference + a few guides" to "verb-first recipe catalog" with structured metadata the agent can match on intent.
2. **Author 8–12 high-leverage recipes** covering the workloads the bench identified as expensive (backlog #5). Each recipe shows the right composition end-to-end, including the workaround patterns.

## Why these go together

#3 without #5: better surface, nothing new to surface — minimal lift.

#5 without #3: more recipes, same discoverability problem — agents still won't find them reliably.

The two together convert the docs surface from "reference the agent searches when stuck" to "playbook the agent reaches for proactively."

## Design — data layer

### Current state

- `tools/codegen/guides.json` — source of truth, 25 chunks today (guides + method docs + 3 existing recipes).
- `data/docs.json` — compiled output (333 chunks total — 25 hand-authored + 308 from Klaviyo OpenAPI auto-extraction).
- `search_docs` tool uses MiniSearch BM25 over the chunks.

### Proposed shape for recipes

Each recipe is a chunk with the existing format plus three new metadata fields:

```json
{
  "id": "recipe.segments.list-with-counts",
  "title": "List all segments with profile counts",
  "platform": "guide",
  "category": "recipe",
  "summary": "Returns all segments + profile_count in a single bulk request using the additional-fields query param. Avoids the 1/s per-segment rate limit.",
  "intents": [
    "largest segment",
    "biggest segment",
    "segments by size",
    "rank segments by profile count",
    "which segment has the most members"
  ],
  "platforms": ["klaviyo"],
  "complexity": "single-call",
  "content": "...",
  "tags": [...]
}
```

Two new fields:
- **`intents`** — natural-language intent phrases the recipe satisfies. **The agent matches on these first.** Phrase as the user would, not as the API does.
- **`complexity`** — `single-call` / `multi-call` / `cross-resource`. Helps the agent estimate cost before reaching.
- **`category: "recipe"`** — distinguishes from `guide` and `method`. Lets us boost recipes in retrieval.

### Search behavior changes

Rework `search_docs` query handling:

1. **Intent-match pass first.** Score chunks by intent-phrase overlap with the query (high weight). Recipes win when the agent's intent maps to a known recipe.
2. **Existing BM25 fallback** when no intent match crosses a confidence threshold.
3. **Result boosting** — recipes get a 2× score multiplier; method docs get 1×; guides get 1×.
4. **Return shape** — top hit always returns full content (not just summary), so the agent can act on it without a second `read_doc` round-trip. Lower-ranked hits return summary-only.

### Inline surfacing in `execute_code` (optional, v1.1.x)

Heavier lift; defer unless v1.1.0 doesn't move the needle. The idea: when `execute_code`'s response would include a result that matches a known anti-pattern (e.g. agent is paginating segments individually to count profiles), the response includes a one-line hint pointing at the relevant recipe. Implementation: tag handlers in `bridge.ts` with anti-pattern detectors that emit hints.

## Implementation plan

### Step 1 — schema update (small)
- Add `intents` + `complexity` to the chunk schema in `tools/codegen/types.ts`
- Update `tools/codegen/docs.ts` builder to validate the new fields when `category === "recipe"`
- All existing chunks default to `intents: []` (no-op for them)

### Step 2 — search behavior (small-medium)
- Update `src/docs/search.ts` MiniSearch config to index `intents` with a high field-weight
- Add a pre-pass that does direct phrase matching on `intents` before BM25
- Add recipe-boost multiplier in the score combinator
- Update `search_docs` tool description to mention recipe-first matching

### Step 3 — author recipes 1–8 (medium)
- Write recipe chunks in `tools/codegen/guides.json`
- Each ~100 lines with: summary, intents (5+ phrases), prerequisites, full code example, expected output shape, common variations, anti-pattern callout
- Run `npm run codegen:docs` to rebuild `data/docs.json`

### Step 4 — author recipes 9–12 (medium)
- Same pattern; these are generalizations from analyst workflows, not bench-observed
- Defer if step 3 already moves the needle

### Step 5 — test coverage
- Add tests in `tests/docs.test.ts` for intent-match retrieval (query phrase → expected recipe hit)
- Snapshot test the search ranking so accidental BM25 regressions are caught

### Step 6 — re-bench
- Re-run all 8 cells of tasks 03 + 07 + 08 (the segment-touching ones) on v1.1.0
- Compare against v1.0.4 baseline (saved) and v1.0.5 delta (from the upcoming re-bench)
- The hypothesis under test: v1.1.0 cuts the segments-task duration in half by eliminating rediscovery time

### Step 7 — release
- Version bump 1.0.5 → 1.1.0 (minor, signals docs restructure)
- Commit + push, user publishes
- Update findings.md and prior-art.md with the v1.1.0 delta

## Expected effort

Rough sizing:
- Steps 1–2: ~half a day combined
- Step 3: ~1 day for 8 recipes (the writing is the bulk)
- Step 4: ~half day for 4 more
- Step 5: ~2-3 hours
- Step 6: ~1 hour to run + judge
- Step 7: ~30 min

Total: ~3 days focused work. Could compress to 2 days if step 4 deferred.

## What we'll learn from the v1.1.0 bench

Three things, in order of importance:

1. **Whether recipe-by-intent solves the discovery tax.** Direct measurement: do tasks 03, 07, 08 stop spending 100s+ rediscovering workarounds? If yes, the pattern generalizes to Shopify and future MCPs we build. If no, the docs aren't the bottleneck — the bridge or the agent's prompt-context handling is.

2. **Whether the conversation-shape effect (task 09 front-load-and-cite) is real or coincidental.** Adding `recipe.front-load-and-cite` and seeing whether v1.1.0 agents adopt the pattern more reliably will tell us.

3. **Whether we should still pursue backlog #7** (partial reversal of the one-tool philosophy with thin enumeration tools). If v1.1.0 closes task 01's +61% gap to within 10–15%, the pure-code philosophy is defensible and #7 is unnecessary. If the gap stays wide, the discussion is worth having.

## Things explicitly NOT in v1.1.0

- API revision override (`apiRevision` per call) — backlog #4, separate small release.
- Per-call overhead audit of `execute_code` — backlog #6, requires profiling work, separate.
- Any decision on backlog #7 (thin enumeration tools) — wait for v1.1.0 numbers.
- Any external blog post or public-facing content — still internal.
